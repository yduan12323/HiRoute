## One allowed post-Pilot performance change

**Proposal:** amortize repeated independent REF seed replay setup, without changing the fixed proposals or physical semantics. Parse the verified immutable table bytes and prepare the REF physical case once per query, then replay each unchanged `(sequence, charges)` through the same accepted `_replay_real` arithmetic. Reparse the original bytes and call the existing public `replay_real_witness_bytes` entrypoint for the selected minimum seed before certifying its depth. Keep the six-file verifier source closure and the original unoptimized entrypoint as the comparison oracle. This is the **single** post-Pilot performance optimization; further changes intended to improve speed require a new explicit review, regardless of their name.

The current repeated path is approximately O(P·(A³ + S²)) parsing and preparation for P proposals, A road anchors and S Sites, plus replay work. Complete-table reachability admission can be cubic in A. Reusing the immutable prepared case should reduce that portion to O(A³ + S² + P·replay), followed by one fresh-byte independent replay of the selected seed. This preserves P, proposal order, charges, numeric type, rejected candidates, accepted minimum, tie rule, certified depth, domain bytes, status, and timeout/memory budgets. It does not reduce the A directed native source runs, eliminate full-table admission, or guarantee that 16/32-Site exact search will finish.

The fixed comparison used OD02, low SOC, both `energy_only` and `energy_and_scheduled` activity modes, nested 8/16/32 Site sets, FLAT then HIER method order, and fresh isolated processes. Every proposal's accepted value or rejection was compared with the original byte-replay path; the selected seed received an independent fresh-byte replay. Normal and `-OO` contract tests passed. The original and corrected Pilot runners charged graph load, native compilation, directed routing, table parse, seed setup, Region setup and search within the same cgroup. Each runner retained an aggregate pre-search setup marker; separate per-function phase timings were **not** captured, so the measured setup improvement cannot be assigned to a precise function from receipts alone. No parameter sweep, candidate reorder, time-window change, or second optimization cycle was performed.

The frozen replay comparison passed every proposal in all six OD02 rows: 93/652/1,752 no-activity and 153/635/1,865 scheduled proposals at 8/16/32 Sites. The winning seed, fresh-byte replay and certified depth matched. The corrected v2 runner then produced twelve separate 120-second/4-GiB receipts. The eight-Site no-activity FLAT/HIER pair retained the same attained exact key; the other ten retained timeout status. At 32 Sites, setup markers fell from 93.956–98.081 seconds to 43.261–43.705 seconds. These are single paired observations, not a completed large-domain speed claim.
