## Observed cost and claim boundary

The fixed six-base-query Pilot contains 18 input rows. Six OD02 rows had independently replayed two-stop seeds; 12 OD00/OD01 rows retained `incumbent_search_failed`. The six qualified rows each ran FLAT and HIER. Only the no-activity eight-Site pair completed: both returned the same attained exact key and both terminal witnesses were independently replayed. Ten method runs timed out. A timeout and a failed finite seed proposal search are not infeasibility evidence.

The marker is durably written **after** graph load, full selected-leg-table routing, seed reconstruction and Region setup, and **before** exact search. The 32-Site methods thus had only about 22–26 seconds of their 120-second wall limit left for search. The stage totals do not isolate each setup subphase. Source inspection gives a strong, testable explanation for the excess: `construct_verified_seed` in `src/timecut5/deployable.py` invokes `replay_real_witness_bytes` for every proposal; that entrypoint reparses the entire immutable N-by-N leg table and prepares the physical case for each call. The source-visible work is at least proportional to proposal count times table size. Proposal count rises about 3× from 16 to 32 Sites while table size rises about 4×; the observed gap between input-gate and search-start time rises from roughly 5 to roughly 54 seconds. This is an inference, not a measured per-function profile. Full-source native routing is also material: the input gate rises from about 14 to 42 seconds across 10 to 32 directed source runs. Region indexing may contribute to the remaining setup gap and needs phase counters before attribution.

On the completed eight-Site case, FLAT attempted 166 extensions; HIER read 166 leaf actions with zero bound-member scans. The HIER run made 1,603 provider queries versus FLAT's 340. This case establishes exact-key agreement, not a performance advantage. It cannot predict the outcome of the timed-out larger rows.

## One allowed post-Pilot performance change

**Proposal:** amortize repeated independent REF seed replay setup, without changing the fixed proposals or physical semantics. Parse the verified immutable table bytes and prepare the REF physical case once per query, then replay each unchanged `(sequence, charges)` through the same accepted `_replay_real` arithmetic. Reparse the original bytes and call the existing public `replay_real_witness_bytes` entrypoint for the selected minimum seed before certifying its depth. Keep the six-file verifier source closure and the original unoptimized entrypoint as the comparison oracle. This is the **single** post-Pilot performance optimization; further changes intended to improve speed require a new explicit review, regardless of their name.

The current repeated path is approximately O(P·N²) parsing and preparation for P proposals and N candidate anchors, plus replay work. Reusing the immutable prepared case should reduce that portion to O(N² + P·replay), with no change to P, proposal order, charges, numeric type, rejected candidates, accepted minimum, tie rule, certified depth, domain bytes, status, or timeout/memory budgets. It does not reduce the N directed native source runs, eliminate full-table admission, or guarantee that 16/32-Site exact search will finish.

Before any rerun, add a phase receipt for graph load, native compilation, directed source routing, table parse, proposal construction, REF preparation/replay, Region setup, and exact search. Validate every proposal's accept/reject and exact key against the original byte-replay path on retained 8/16/32 tables, including failures, coattached Sites, scheduled windows, and `-OO`; require the final seed and depth bytes to match. Review source closure and fail closed on any disagreement. Then run **one** paired, same-input 8/16/32 benchmark under unchanged 120-second/4-GiB cgroups, including all setup, with source hashes and separate measured CPU. Preserve the original Pilot outcomes. No parameter sweep, candidate reorder, time-window change, or second optimization cycle is proposed.

## Necessary functionality, outside that optimization

- **Table-free certified selected-leg provider:** the current Pilot computes a complete ordered-leg table before search. A deployable path must bind graph, routing binary and tie policy, Site/anchor identity, and source bytes; compute selected legs only for requested directed sources; retain native predecessor-edge witnesses; and validate conservative directed ALT without a full table's exact source-to-Region minimum. It needs an independent edge-level certificate and fail-closed admission for new entries. The present `RegionBoundProvider` validates ALT against every frozen table minimum and materializes source × Region × member bounds, so calling the same full-table adapter “on demand” would not satisfy this gate. Routing/graph/landmark setup and cache misses must be charged. This is a missing capability, not permission to alter the one performance proposal.
- **Live OPEN checkpoint and recovery:** the existing token binds prepared inputs before search. Recovery requires a complete, versioned serialization of OPEN/frontier pieces, incumbent, counters, source closure, exact numeric state and all dependencies, then independent validation that resumed search has identical status and exact key to uninterrupted search under normal and `-OO` execution. Partial or mismatched state must fail closed. This is necessary interruption functionality; no claimed warm-resume result exists.
